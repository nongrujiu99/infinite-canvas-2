# 平台视觉系统：平台 × 场景 × 属性联动

## 为什么不是「再加几十个风格」

原来的 `EcomStyle` 把两件不同的事写在同一个字段里：

```
scene      → 具体地点（书桌、窗台、纯白背景纸）
lighting   → 光质光比
composition→ 构图
keywords   → 观感倾向
```

所以每套风格天然自带一个背景和一种光。12 套风格其实是 12 个「背景 + 光 + 台子」的组合，
换风格只是换块背景布，构图逻辑和场景结构始终不变——这就是「风格越多越单调」的根因。

正确的拆法是正交的三层，任何一层变化都不会被另外两层绑死。

---

## 三层模型

### 第一层：平台审美语言（`constant/ecom/platforms.ts`）

回答「这张图像哪个平台」，**不含任何具体地点**。

同一张「桌面」，天猫要亮净贵、亚马逊要中性写实、小红书要随手拍、品牌 KV 要留白叙事。
差别不在道具，而在光比、饱和、留白、修图程度和道具纪律。

每个平台固定七个字段：

| 字段 | 作用 | 落到提示词 |
|---|---|---|
| `look` | 审美总述 | `[Platform look]` |
| `lighting` | 光质、光比、色温 | `[Lighting]` |
| `color` | 饱和、对比、白平衡 | `[Platform look]` |
| `composition` | 主体占比、留白位置 | `[Composition]` |
| `styling` | 道具密度与造型语言 | `[Platform look]` |
| `realism` | 修图程度 | `[Platform look]` |
| `safeArea` | 文案安全区坐标 | `[Composition]` |

外加三个硬约束：`propLimit`（道具上限）、`human`（是否允许手/人入镜）、`defaultRatio`。

**平台规范速查**

| 平台 | 比例 | 产品占比 | 硬约束 |
|---|---|---|---|
| 亚马逊主图 | 1:1 ≥1000px | ≥85% | 纯白 RGB255、无阴影、无文字、无道具、禁模特 |
| 亚马逊辅图 2–9 | 1:1 | 自由 | 场景/细节/尺寸/包装/信息图，7 张用满转化高 20–35% |
| 天猫主图 | 1:1 800+ | 第 5 张白底 70–80% | 第 1 张禁「牛皮癣」，否则搜索降权 |
| 小红书 | 3:4 | 自由 | 文字面积 ≤30%，否则判低质营销图 |
| 品牌 KV | 4:5 或横版 | 30–40% | 大面积留白给标题与 logo 组合 |

### 第二层：物理场景（`constant/ecom/scenes.ts`）

回答「产品被放在哪里」。13 个场景：桌面 / 窗边 / 床头 / 厨房 / 浴室 / 玄关 / 客厅 / 户外 / 咖啡馆 / 车内 / 健身房 / 影棚 / 参考图场景。

承托面刻意拆成三段：

```ts
surfaceMaterial: "smooth matte wooden"   // 材质形容词，可被规则替换
surfaceNoun:     "desktop"                // 承托物，材质规则永远不改它
surfaceNote:     "with faint open grain"  // 固定修饰
```

不拆的话，一件深色铝合金产品会让**客厅的茶几**变成「深色木桌面」——材质对了，场景错了。

`props` 只放交代地点的中性道具（桌面上有笔记本才像桌面），与产品属性无关。

### 第三层：属性联动（`constant/ecom/scene-rules.ts`）

回答「这个产品的场景里还该有什么」。从识别结果推：

```ts
material → metal / glass / leather / fabric / silicone / wood / ceramic / plastic / paper / stone
tone     → dark / light / neutral（按主色相对亮度，阈值 0.38 / 0.70）
glossy   → 亮面 vs 哑光
category → 使用语境
```

规则分四组，按权重取：

| 组 | 权重 | 输出 |
|---|---|---|
| 品类语境 | 86–92 | 充电器旁边有第二台设备，桌搭旁边有眼镜和便签 |
| 材质呼应 | 68–80 | 深色金属 → 深色木面；只改材质形容词，不改承托物 |
| 色调平衡 | 40–52 | 只产提示语，不加道具（深色产品别融进背景） |
| 场景特化 | 100 | 影棚 = 清空道具并锁定承托面 |

三条硬规则，都是先踩坑后加的：

1. **`clearsProps`** —— 影棚不是「道具少」而是「根本不该有」。只把上限写 0 不够，其他规则还会往里塞。
2. **`excludeScenes`** —— 唱片封套、便签、鼠标都属于室内陈设，放在草地和车里讲不通。
3. **不能与产品同类** —— 耳机产品的场景里绝不能再出现一副耳机，模型会画成两副并挑错主体。

## 提示词结构

```
[Priority] [Image roles] [Product lock] [Product finish] [Branding] [Controls]
[Camera] [Framing] [Scale]
[Platform look]   ← 新增：这是什么类型的图
[Scene] [Support]
[Scene props]     ← 新增：属性推导的道具
[Operator notes]
[Lighting] [Color] [Composition] [Style] [Realism] [Avoid]
```

分工刻意不重叠，同一件事说两遍模型就会挑一条听：

- 光 → `[Lighting]`，`platform.lighting + scene.lightSource`
- 构图与安全区 → `[Composition]`
- 平台总述 / 色彩处理 / 道具纪律 / 修图标准 → `[Platform look]`
- 具体摆什么 → `[Scene]` 与 `[Scene props]`
- 明暗分离 → `[Color]` 追加句

三个新参数不传时，提示词与加这套之前**逐字一致**（`identical` 保证）。

## 与旧路径的关系

`EcomStyle` 保留为「视觉配方」，只在需要固定复用某套观感时用，选中后整体覆盖平台与场景。
两条路径互斥——共存会让「配方自带纯白背景」和「场景选了窗边」同时进提示词。

存档升级到 v2 时清空一次 `styleId`，让老用户能看到新组合；自建风格本体不受影响。

---

## 文字不要交给 AI 生成

海报和 KV 的文字让模型画必然出现乱码。正确做法是 AI 只出带安全区的底图，文字由前端按坐标叠加。
所以 `safeArea` 是坐标数据 + 提示词里的「方位 + 占比 + 禁止项」三件套，不能只写一句「留白」——
只说留白，模型会把细节铺满。

## 场景库：与视觉配方同构的管理

场景不是一张写死的常量表，它需要和视觉配方一样能被改、被停用、被复制、被新建。否则「加场景」永远要改代码。

| | 视觉配方 | 场景 |
|---|---|---|
| 存储 | `overrides`（内置覆盖层）+ `custom`（自建） | 同 |
| 内置项 | 只读，改动存差异字段 | 同 |
| 可做 | 编辑 / 停用 / 复制 / 恢复默认 | 同 |
| 入口 | 05 区块「管理风格」 | 02 区块「管理」 |

两者共用一个弹窗的两个页签。分开两个入口的结果是用户根本不知道场景也能改——而场景恰恰是这里最需要控制的一层。

### 一个必须存在的字段：行为归类

规则（`scene-rules`）是按**场景 id** 写的：桌面才有台面、影棚要清空道具、户外不该出现唱片封套。自建场景的 id 永远不在这些数组里，所以它必须声明「我像哪一类」：

```ts
type EcomScene = {
    id: string;            // 内置是 desk / window…，自建是 custom-scene-xxx
    family?: EcomSceneId;  // 行为归类，规则按它匹配
    surfaceMaterial: string;  // 材质形容词，可被属性规则替换
    surfaceNoun: string;      // 承托物名词，规则永远不改它
    …
};
```

没有 `family`，自建场景就只是一张不参与联动的背景布——材质呼应、道具纪律、场景特化全部失效，而界面上完全看不出来。所以编辑器把「行为归类」放在承托面之上，并明确写出「当前按 X 套用规则」。

### 从场景图识别新建

和「从风格图识别」共用同一个多模态模型，但问的是另一件事：

- 风格识别问审美语法：光比、构图、配色、关键词
- 场景识别问地点本身：承托面（材质 + 名词）、背景、光源、景深、交代地点的道具、行为归类

所以两个 prompt 里都有一条相同的前提：**图里的产品是占位符，不许描述它**。区别在于风格拆解还要剔掉平台特征（平台是另一层），场景拆解不涉及平台。

识别失败（既没有承托物也没有背景）时明确报错并保留手动新建，不落半套场景——半个场景拼出来的 `[Scene]` 是一句没有地点的废话，校验也过不去，用户会撞上「识别成功但存不了」。
